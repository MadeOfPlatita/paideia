## Defaults técnicos unificados propuestos

1. **Catálogo/runtime:** web estática servida desde hosting público, independiente del PC del equipo; snapshot JSON versionado de solo lectura, con campos y citas por procedencia. PostgreSQL solo detrás de un repositorio backend si se demuestra necesario y se aprueba su servicio; el modelo no conecta directamente a la DB.
2. **Chat:** un LLM real detrás de un gateway de servidor con secreto no expuesto al cliente. La aceptación exige una llamada real aprobada; stub/FAQ sirven para pruebas o contenido estático, nunca se anuncian como IA. Si el gate de proveedor no pasa, chat marcado bloqueado; no auto-pago ni fallback generativo fingido.
3. **Tools:** allowlist cerrada de catálogo/búsqueda/detalle/comparación/fuentes y cálculo determinista. Solo un ciclo por turno, argumentos/resultados validados por backend, lectura/código puro; consultas predefinidas y parametrizadas. Sin tools de escritura, SQL libre, URL arbitraria, compra o contratación. El proveedor elegido debe soportar tools para cumplir ese flujo; no rebajar el requisito en silencio.
4. **Perfil/contexto:** en memoria local; persistencia local solo tras opt-in explícito y borrado visible. Selector educativo local; no adjuntar perfil completo ni historial. Cualquier campo contextual transmitido se selecciona por separado para una solicitud y se muestra antes de enviar; cantidades financieras requieren aprobación expresa y cierre de privacidad/proveedor.
5. **Datos y simulación:** conservar valores desconocidos como `unknown/null` con motivo, no como cero o ausencia universal; separar fechas efectiva, observada y consultada. Bloquear solo campo/uso no respaldado. Productos reales en catálogo/comparador; escenario con importes e interacción ficticios, sin transacción real.
6. **Abuso/capacidad:** límite efímero por sesión, cola justa, reserva/presupuesto global 0 €, concurrencia limitada y sin retry automático. NAT no es identidad. Fallback significa disponibilidad de funciones locales/estáticas y mensaje honesto, no reemplazo del chat real. Smoke externo solamente bajo condiciones documentadas y autorización; carga real de 100 requiere permiso y prueba independiente.
7. **Visualización/exportación:** SVG+tabla, interfaz semántica; impresión con CSS, sin servicio PDF externo. PDF opcional pospuesto hasta validar la ruta esencial, tiempo y licencias.

## Decisiones de grupo realmente consecuentes (3–5)

No hacen falta 14 respuestas técnicas. Los defaults anteriores absorben elecciones de implementación recuperables; estas decisiones sí cambian privacidad, coste, alcance o publicación:

1. **Transmisión de datos financieros contextuales:** ¿se permite que campos económicos seleccionados salgan del navegador a un proveedor LLM, con qué aviso/elección por petición? Default seguro: no enviar cifras ni perfil automáticamente; si no se aprueba, el contexto externo se limita a mensaje/tema escogido.
2. **Cero euros vs. disponibilidad del LLM público:** si ningún proveedor gratuito permite el uso público requerido bajo condiciones aceptables, ¿se mantiene bloqueado el chat para publicación o se revisa explícitamente el presupuesto/condiciones (incluida tarjeta)? No aceptar términos, activar facturación ni cambiar plan automáticamente.
3. **Cobertura de productos para la demo:** fijar un mínimo medible de cobertura en las cinco familias y aceptar por adelantado cómo se presenta una familia/campo que sigue sin permiso o evidencia. No usar datos inventados para cumplir una cuota; «90 % de populares» sigue sin definición.
4. **Afirmación de capacidad ante la clase:** decidir si se invita públicamente solo tras superar las pruebas de 100 del plan, o se acepta una demo con funciones estáticas disponibles y chat best-effort/limitado sin promesa de 100 respuestas.
5. **Publicación open source:** confirmar titulares de contribuciones y licencia del código antes de hacer público el repositorio; la licencia de código no concede derechos de datos, marcas o fichas.
